## D-001 · 위기 표현은 항상 규칙으로, 추천보다 먼저 검사
- 날짜: 2026-11-11 (프로토타입 v4) · 상태: **채택**
- 고려한 안: ① AI가 위기 여부까지 판단 ② 규칙으로 먼저 거르고 AI는 보조
- 결정: ②. 위기 표현 목록(`CRISIS`)을 추천보다 먼저 검사하고, 걸리면 책 대신 109 안내를 보여 준다.
- 이유: 안전 기능은 결과가 매번 같아야 하고, 네트워크나 AI 오류가 나도 동작해야 한다.

## D-002 · 공개판은 규칙 방식만, AI 탭은 프로토타입에 보존
- 날짜: 2026-11-24 · 상태: **변경됨 → D-008** (2026-11-25)
- 배경: 프로토타입 v4의 AI 탭은 claude.ai 안에서만 동작해서 GitHub Pages에서는 쓸 수 없었다.
- 고려한 안:
  ① Firebase Cloud Functions로 Claude API 호출 (유료 요금제, API 비용, 키 관리, 호출 상한 필요)
  ② 규칙 방식만 공개하고 AI 비교는 `prototype.html`에 기록으로 남김
- 결정: ②
- 이유: 비용 없이 바로 출시해 실제 사용자 반응을 먼저 본다. "감정 못 찾음" 비율이 목표(20%)를 넘으면 그때 AI 도입 근거가 된다.

## D-003 · 입력한 문장은 저장하지 않는다
- 날짜: 2026-11-24 · 상태: **일부 변경 → D-009** (저장하지 않는 원칙은 유지)
- 고려한 안: ① 문장 원문 저장 (사전 보강에 유용) ② 감정 이름, 사전 단어, 경로만 저장
- 결정: ②
- 이유: 감정 문장은 민감한 개인 정보에 가깝다. 특히 위기 표현을 저장하면 책임질 수 없는 데이터가 생긴다. 사전 보강은 "감정 못 찾음" 비율과 피드백으로 대신 판단한다.
- 대가: 어떤 문장에서 감정을 못 찾았는지 알 수 없다. 대신 테스트 케이스와 베타 테스트로 보완한다.

## D-004 · 빌드 도구 없이 HTML·CSS·JS 모듈로 구성
- 날짜: 2026-11-24 · 상태: **채택**
- 고려한 안: ① React/Vite ② 바닐라 JS ES 모듈
- 결정: ②
- 이유: 화면이 두 개뿐이고 GitHub Pages에 그대로 올릴 수 있다. 설치 없이 누구나 열어 볼 수 있다. `dist/`는 `build.ps1`로 필요한 파일만 복사해 만든다.

## D-005 · 운영자 권한은 Firestore `admins` 컬렉션으로 판단
- 날짜: 2026-11-24 · 상태: **채택**
- 고려한 안: ① 운영자 화면에 비밀번호 하드코딩 ② Firebase Auth + `admins/{uid}` 문서 존재 여부
- 결정: ②
- 이유: ①은 소스에 비밀번호가 노출된다. ②는 보안 규칙에서 서버가 직접 확인하므로 화면 코드를 고쳐도 데이터를 읽을 수 없다. 운영자 추가는 Firebase 콘솔에서만 가능하다.

## D-006 · 감정 단어에 과거형 추가
- 날짜: 2026-11-24 · 상태: **채택**
- 배경: 테스트에서 첫 화면 예시인 "요즘 너무 지쳤어"가 감정을 찾지 못했다. 사전에 "지쳐, 지친"만 있고 "지쳤"이 없었다.
- 결정: 지쳤, 슬펐, 화났, 떨렸, 신났, 기뻤, 설렜, 그리웠, 멍해를 추가했다.
- 이유: 사람들은 지난 일을 과거형으로 말하는 경우가 많다. 어간만 넣는 방식은 받침이 바뀌는 활용형을 놓친다.

## D-007 · 공유 링크는 문장이 아니라 감정 이름만 담는다
- 날짜: 2026-11-24 · 상태: **채택**
- 결정: 공유 링크는 `?emo=불안&utm_source=share` 형태로 만든다.
- 이유: 친구에게 보내는 링크에 내 속마음 문장이 그대로 들어가면 공유하기 꺼려진다. 감정 이름만 있어도 같은 책 3권을 보여 줄 수 있다.

## D-008 · 블로그로 확장하고 Claude AI를 다시 도입 (중계 서버 방식)
- 날짜: 2026-11-25 · 상태: **채택**
- 배경: 과제 주제가 "내 블로그에 독자 또는 관리자를 위한 AI 기능을 넣어 워크플로우 자동화"로 정해졌고, Claude API 키(무료 크레딧)를 받았다. 블로그가 따로 없어 감정책 사이트를 블로그로 키우기로 했다.
- 고려한 안 (AI 호출 위치):
  ① 브라우저에서 바로 Claude 호출 (GitHub Pages는 코드가 공개되어 키가 그대로 노출됨)
  ② Firebase Cloud Functions (Blaze 요금제로 바꾸고 카드 등록 필요)
  ③ Cloudflare Workers (무료, 카드 불필요, GitHub 저장소 연결로 브라우저에서 배포 가능)
- 결정: ③. 키는 Worker Secret에만 두고, 블로그는 `js/ai-config.js`의 Worker 주소만 안다.
- 이유: 키 노출 없이 비용 0원으로 운영할 수 있고, 내 PC에 Node가 없어도 배포할 수 있다.

## D-009 · 독자 문장은 Claude에 보내되 저장하지 않는다 (D-003 개정)
- 날짜: 2026-11-25 · 상태: **채택**
- 고려한 안: ① 지금처럼 브라우저 밖으로 보내지 않음 (AI 사용 불가) ② 감정을 읽을 때만 Claude에 보내고, 블로그·Worker 어디에도 저장하지 않음
- 결정: ②. AI가 켜지면 첫 화면 안내 문구를 "AI(Claude)에 보내지만 저장하지 않습니다"로 바꿔 알린다. 위기 표현은 보내기 전에 브라우저에서 먼저 거른다.
- 이유: 상황만 말한 문장을 읽으려면 문장 전체가 필요하다. 대신 저장하지 않고, 위기 문장은 아예 보내지 않으며, 독자에게 사실대로 알린다.

## D-010 · AI 결과는 사람이 확인한 뒤에만 발행한다
- 날짜: 2026-11-25 · 상태: **채택**
- 고려한 안: ① 메모를 넣으면 AI가 바로 발행 (완전 자동) ② AI가 칸을 채우고 운영자가 고친 뒤 직접 발행
- 결정: ②. 글쓰기 화면을 "1. 내가 쓰는 부분 / 2. AI가 채우는 부분 (고칠 수 있어요)"으로 나눴다.
- 이유: AI가 메모에 없는 줄거리나 인용을 지어낼 수 있다. 블로그 글의 주인은 운영자이고, 자동화의 목표는 "확인만 하면 되는 상태"까지다.

## D-011 · AI가 실패하면 규칙 방식으로 이어간다
- 날짜: 2026-11-25 · 상태: **채택**
- 결정: AI 주소가 비어 있거나, 호출이 실패하거나, 20초를 넘기거나, 답이 형식에 맞지 않으면(감정이 12가지 밖, 없는 글 id) 규칙 방식으로 보여 준다. 관리자 도우미도 규칙 버전(`localAssist`)으로 칸을 채운다.
- 이유: 크레딧 소진이나 Worker 장애가 블로그 장애가 되면 안 된다. 테스트 AI1~AI4, A1~A6이 이 경로를 확인한다.

## D-012 · AI 중계 서버의 관리자 확인은 Firestore 규칙에 맡긴다
- 날짜: 2026-11-25 · 상태: **채택**
- 고려한 안: ① Worker에 관리자 UID 목록을 따로 적음 ② Firebase 토큰 서명을 Worker에서 직접 검증 (라이브러리 추가) ③ 로그인 토큰으로 Firestore `admins/{uid}`를 읽어 봄
- 결정: ③
- 이유: 관리자 목록을 한 곳(Firestore)에서만 관리한다. 토큰이 가짜거나 만료되면 Firestore가 거부하고, 규칙상 본인 문서만 읽을 수 있어 다른 사람 UID로 속일 수 없다.

## D-013 · 모델은 claude-opus-5-5, 크레딧이 부족하면 바꾼다
- 날짜: 2026-11-25 · 상태: **채택**
- 결정: 기본 `claude-opus-5-5`. 독자 추천은 effort `low`, 관리자 도우미는 `medium`. 응답은 JSON Schema로 고정하고, 안전 분류기가 거절하면 서버 측 fallback으로 다른 모델이 이어받는다.
- 이유: 한국어 문장의 미묘한 감정과 운영자 말투 유지에는 성능이 높은 모델이 낫다. 비용이 문제가 되면 `wrangler.toml`의 `MODEL`만 `claude-haiku-5-5`로 바꾸면 된다 (코드 수정 없음).
